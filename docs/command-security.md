# Stage 1 Command-Level Security

This stage defines three core protections:

1. Ed25519 command signatures for tamper detection.
2. Sequence and timestamp checks for replay protection.
3. A vehicle watchdog that enters the configured safety state when valid commands stop.

## Gateway Interface

The Gateway owns control-session creation and public-key binding. The public key is generated by the browser and is associated with the authenticated operator, vehicle, and short-lived session. The current implementation uses the Control Session endpoints documented in `docs/architecture.md`; storage and lease semantics are implemented by the Gateway and Redis.

## Browser Sender

The browser generates a temporary Ed25519 key pair, acquires a Control Session, and signs each control message. A message contains its version, type, session ID, sequence, timestamp, command, and signature before it is sent through the LiveKit DataChannel.

The private key is kept only in page memory. It must not be persisted, placed in a URL, or sent to the Gateway.

## Vehicle Verification

The vehicle accepts a command only when:

- The session is active and belongs to the authenticated operator.
- The session ID and vehicle identity match.
- The signature validates against the session public key.
- The timestamp is within the configured acceptance window.
- The sequence is strictly newer than the last accepted sequence.
- The command is received before the session expires.

Invalid, stale, duplicated, or unverifiable commands must be rejected and audited where applicable.

## Watchdog and Emergency Action

The vehicle watchdog monitors the time since the last valid control message. When the timeout is exceeded, it clears the trusted control state and invokes the configured emergency action. The real CAN/ECU emergency-brake actuator is not connected in this prototype.

## End-to-End Tests

Gateway and browser protocol tests run in this repository:

```bash
(cd apps/teleop-gateway && go test ./...)
npm --prefix frontend test
```

Vehicle signature, replay and watchdog tests now belong to `apollo-base`.
The former Python vehicle/security runners were removed; see
[vehicle deployment](deployment.md#vehicle-deployment) for the external test
boundary. Local tests do not qualify physical actuation.

## Production Requirements

- Store public-key/session state in a durable, TTL-controlled backend when required by the deployment topology.
- Keep private keys non-persistent in the browser.
- Connect a reviewed physical safety actuator before any real vehicle test.
- Synchronize clocks with NTP/PTP when using tight timestamp windows.
- Preserve structured audit events for acquisition, renewal, release, rejection, timeout, and emergency action.
