# Remote-control timestamps and timeout diagnosis

Start with the **first fault** in the operator’s `teleop-diagnostics.json`. Match it to the same vehicle, control session, receiver instance, revision, and command sequence in the vehicle evidence. The Gateway grants and renews authority over HTTP. Signed commands and their feedback travel between browser and vehicle over LiveKit. A successful lease renewal and a vehicle command ACK therefore measure different paths.

## First-fault lookup

| First symptom or reason | First comparison | What it isolates |
| --- | --- | --- |
| `stale_command` | At vehicle validation, compute **vehicle wall time in ms − signed `timestamp_ms`**. The receiver inspected accepts **−150 through +450 ms**, inclusive. | Below −150 means the stamp appears too far in the future. Above +450 means the command appears too old. Check clock offset and elapsed delivery time separately. |
| `not_authorized` | Check receiver status, then vehicle steady `now − received` for that packet. A negative interval or one ≥250 ms fails this check. | An already locked or disabled receiver produces the same reason. A packet can also wait too long locally even with synchronized host clocks. |
| `command_paused` / `command_timeout` | Vehicle steady time since receipt of the last **accepted** command. Default pause ≥300 ms, lock ≥1,500 ms. | Inspect the last advancing sequence, then browser dispatch gaps, loss, or intervening rejections. This watchdog starts after the first accepted command. |
| `context_expired` / `authority_expired` | Vehicle context deadline = HTTP request start on vehicle steady clock + min(returned `ttl_ms`, context cap). Default cap 5,000 ms. | The response arrived after its deadline, or the installed context subsequently expired. Check context polling, HTTP duration, remaining lease TTL, and revision. |
| `send_stalled` / `ack_timeout` | Browser time since send began ≥255 ms, or since oldest pending dispatch ≥600 ms by default. Compare `tick → sign → dispatch → published` and matching `ack`. | The former covers signing/publication. The latter covers forward delivery, vehicle handling, feedback delivery, and browser callback scheduling. |
| `authority_or_feedback_timeout` | In order, check `lease_remaining_ms`, RTC reconnect interval (default 1,200 ms), then elapsed time since connection or last valid feedback. Initial feedback >5,000 ms, subsequent feedback >1,000 ms by default. | The fault code is shared. Repeated feedback can keep the feedback timer healthy while the accepted sequence stops advancing. |
| Three moving cameras, request disabled, or `media_lost` | Compare `presented`, `verified`, age percentiles, and `longest_gap_ms` **per camera**. Also check `receiver_ttl_ms` and `control_request_blocker`. | Zero verified samples leaves source age unknown. Expired heartbeat, missing frame metadata, expired clock sample, and a lease/handover blocker have different remedies. |
| Guardian `remote_cmd_timeout` or Canbus freshness fault after an ACK | Follow the accepted sequence into the Cyber command, then inspect Guardian’s selected source stamp and Canbus’s reported source age or last valid receive age. | Locates a downstream failure after receiver acceptance. An ACK alone cannot show when the chassis acted. |
| Handover still pending | Inspect edge revocation and the first Guardian and chassis samples after the fence. | A browser poll timeout ends its wait. The vehicle needs fresh evidence of exit before physical handover can be confirmed. |
| Telemetry `clock-error` or media demand HTTP 503 | Identify the endpoint. Compare telemetry fields with Gateway wall time, or check Redis logs for `media demand clock moved backwards`. | Telemetry source/publisher skew and Redis demand time regression are independent of signed-command age. A generic 503 alone cannot identify clock regression. |

Numbers above are defaults unless identified as receiver checks. Save the acquire/renew and vehicle context `timing_policy` from the incident. Vehicle checks here were read from the Apollo working tree at revision `e5a89a1f19` on November 26, 2026. Match the deployed binary and Guardian configuration before applying those thresholds elsewhere. ## Gateway and Redis clocks

| Endpoint or stage | Field and clock | How to use it |
| --- | --- | --- |
| Control acquire / renew | `session.created_at_ms`, `session.expires_at_ms`, `server_time_ms` are Gateway Unix milliseconds. `renew_after_ms` is a duration, normally half the 30 s lease. | Acquire samples Gateway time during request handling. Renew returns a fresh time. Browser schedules renewal and expiry from its own request **start** plus one and two renewal intervals respectively. HTTP budget is 3 s, initial RTC join budget 5 s. |
| Vehicle control context | `ttl_ms` is Redis remaining control lease lifetime in ms. `context_ttl_ms` is a policy cap. `revision` orders changes to authority. | A slow context request consumes its own validity. On the receiver, compare the returned lifetime with request duration and time since the last successful refresh. |
| Receiver presence | A native context poll refreshes a separate Redis key for 5 s. Bench-clock returns its remaining `receiver_ttl_ms` (zero when expired). | Browser presence expires at request start + min(TTL, 5,000 ms). This shows recent receiver polling. Command delivery requires separate evidence. |
| Viewing lease / vehicle media demand | `server_time_ms` comes from Redis TIME. `expires_at_ms` (viewing) and `valid_until_ms` (demand) use that same Unix-ms clock. Demand `retry_after_ms` is a poll interval. | Subtract server time from the corresponding deadline, then add the result to local monotonic request start. Demand is capped at 5 s and recommends polling every 1 s. Equal revisions can carry renewed validity. Keep the demand UUID epoch with the revision. |
| Camera bench-clock | Numeric `epoch` identifies a Gateway process. `elapsed_ms` is monotonic time since that process started. | Only compare a camera stamp with a sample from its own epoch. A restart or requests reaching different processes can invalidate a comparison. The demand UUID and the camera epoch serve separate purposes. |

## Browser command, vehicle validation, and return feedback

1. **Calibrate.** On successful acquire/renew the browser computes HTTP RTT from two `performance.now()` readings. It estimates `clockOffsetMs = round(server_time_ms + RTT / 2 − Date.now())`. A missing or unusable sample leaves the previous offset in place (initially zero). A long or asymmetric request introduces uncertainty. This calibrates the browser to the Gateway. Vehicle-to-Gateway skew still contributes to apparent age.
2. **Stamp and dispatch.** The browser assigns signed `timestamp_ms = max(1, round(Date.now() + clockOffsetMs))` **before** asynchronous Ed25519 signing. It records `dispatch` immediately before calling publish and `published` when the promise resolves. A `superseded` intent can use a sequence without sending a packet. A gap in dispatched sequence numbers alone cannot establish packet loss.
3. **Validate.** The vehicle checks the local receive-to-handler interval on its steady clock and the signed stamp against vehicle Unix ms. Apparent command age includes signing, transport, local queueing, and residual clock offset. For example, if a rejected packet appears 480 ms old and vehicle UTC is 200 ms ahead of calibrated sender time, elapsed time is roughly 280 ms, subject to calibration error. The receiver still compares **480 ms** with its 450 ms limit.
4. **Acknowledge.** Feedback carries `accepted_sequence`, `status`, `reason`, and `last_rejection`. It has no vehicle event timestamp. Match the browser `ack` to that sequence. Its `duration_ms` measures dispatch to receipt of the matching ACK on one browser clock. Feedback can arrive before the publish promise settles. On RTC recovery, the browser resets pending dispatch deadlines and the feedback timer, so an ACK duration spanning reconnect is measured from recovery.

## Vehicle Cyber, chassis, and handover

| Stage | Timestamp to follow | Diagnostic use |
| --- | --- | --- |
| Edge → `/apollo/teleop/control` | `header.timestamp_sec` is vehicle Unix time at Cyber publication in seconds. `header.sequence_num` belongs to the Cyber publisher. | Use the edge’s accepted-sequence/Cyber-sequence correlation where available. `latency_stats.total_time_ms` measures local publisher work from steady-clock entry to measurement. It excludes browser signing and network transit. |
| Guardian arbitration | Compares selected input `header.timestamp_sec` against vehicle `now_sec`. Freshness uses signed age in ms and checks both past and future limits. | The inspected Guardian config uses 150 ms for remote takeover, 300 ms for ongoing remote commands, 200 ms each for auto commands and planning, and 100 ms for chassis. Inspect the input named in the fault. |
| Guardian → Canbus | `GuardianCommand.source_timestamp_sec` preserves the selected upstream stamp. Guardian also emits its own publication header. Canbus restores the source stamp into the selected control command and converts seconds to microseconds for its freshness monitor. | Read Canbus’s reason and reported `timeout_ms`. An old or future source stamp concerns command production. `last_rx_age_ms` measures the interval since the last valid command received. A recently published Guardian envelope can carry an old source. |
| Physical handover | Vehicle records a steady-clock fence and a wall-ms fence at revocation. Each Guardian status and chassis sample has a steady receive time and a wall source stamp. | Both times must be strictly after their respective fences, no later than their respective current times, and at most 1 s old. Check native producers and agreement on manual/auto mode. The browser polls every 200 ms for up to 10 s. |

## Vehicle camera → Gateway clock → displayed frame

| Stage | Timestamp, units, and interpretation |
| --- | --- |
| Capture and encode | GStreamer PTS is a stream timestamp. Apollo converts PTS through the segment to running time, adds pipeline base time, and obtains `capture_monotonic_us` on a supported monotonic pipeline. Encoded `timestamp_us` is media timing. `capture_time_us` is the separate wall-clock field carried as `user_timestamp_us`. The physical-camera freshness calculation uses the monotonic field. |
| Map capture to the Gateway | The vehicle worker samples bench-clock. For a matching sample, let `d` be whole milliseconds from vehicle steady receipt of the sample to capture. For 0 ≤ d ≤ 15,000, the encoded lower bound is `elapsed_ms + d − (floor(d / 1000) + 1)`. The worker attaches camera ID, epoch, stamp, and CRC to frame metadata. Generated bench frames can carry the stamp optically. |
| Identify the displayed frame | The browser uses the frame callback’s `rtpTimestamp` to look up metadata on that track. RTP timestamps identify media frames within a stream. `presentedFrames` counts presentation progress. For physical video check metadata negotiation, especially `CAP_PACKET_TRAILER`, and camera ID, epoch, and CRC. |
| Verify source age | Browser samples bench-clock with monotonic `started` and `received`. At callback time `now`, the upper age bound in ms is `elapsed_ms + 1.001 × (now − started) + 2 − stamp`. Require ordered times, a clock sample at most 15 s old, and **0 ≤ bound < 1,000 ms**. Each of three current tracks needs 1,000 ms of continuous valid evidence. Duplicate stamps cannot extend a deadline. |
| Isolate browser delay | `receiveTime`, `presentationTime`, and callback time are browser-local ms. Local residence is the maximum of zero, presentation minus receipt, and callback minus receipt. A large value points to delay after reception. For rising source age with low local residence, inspect capture, encode, transport, and clock samples upstream. |
| Read the export | `camera_windows[].start_ms` is browser monotonic, `duration_ms` is window length, and `longest_gap_ms` is a presentation gap that can include startup. Read `verified` alongside `age_p50_ms`, `age_p95_ms`, `age_p99_ms`, and `age_max_ms`. Null with zero verified means the window contains no measured source-age bound. |

## Telemetry clocks

Follow each chassis or localization sample through **`source_timestamp_ms` → `published_at_ms` → `received_at_ms` → `server_time_ms`**. These are respectively the upstream vehicle source time, vehicle snapshot publication, Gateway receipt, and Gateway response wall time. `sample.age_ms` is elapsed age since the vehicle’s local callback at snapshot creation. Use `stream_id`, `sequence`, and `source_sequence` to spot a fresh envelope carrying an unchanged sample.

The directory client adds elapsed browser monotonic time since fetch start to its ages. A source, publisher, or receipt stamp **more than 5 s ahead** of response time yields `clock-error`. A missing source stamp yields unknown freshness when the clocks otherwise pass. The detailed data view applies its own **100 ms** future tolerance. Identify the screen before interpreting a clock alert. To localize delay, compare source vs publication, publication vs receipt, and receipt vs response, allowing for measured clock offset at each host boundary. ## Reconstruct an incident

1. Export `teleop-diagnostics.json` promptly while the controller is available. Keep the UTC interval, vehicle ID, deployed revisions, receiver mode, session/revision, applicable timing policy, and relevant Gateway and vehicle log lines. The control trace retains 128 events. The export can have empty `events` after controller teardown even when camera windows remain. Retain only timing and identity fields from API responses, which can also contain tokens.
2. Sort `events` and `timeline_events` by `monotonic_ms` within **one tab**. For an approximate UTC join to logs use `time_origin_ms + monotonic_ms`. For durations subtract monotonic readings directly. A change in `wall_elapsed_delta_ms` shows browser wall elapsed time diverging from monotonic elapsed time since trace start. It does not identify the vehicle’s clock offset.
3. For suspected skew, bracket a remote wall-clock sample with local wall send and receive times. With stable clocks, **remote minus local** lies between `remote − local_receive` and `remote − local_send`. Repeat near the incident on Gateway and vehicle against the same reference, retaining the interval widths. A later NTP status cannot establish the offset at the incident time.
4. State what the evidence resolves. For example, a dispatch at browser 12,000 ms, repeated feedback with the previous accepted sequence, and `ack_timeout` at 12,605 ms establish a missed 600 ms ACK budget. Vehicle rejection or receipt evidence for that sequence is needed to distinguish forward loss, receiver rejection, or delayed feedback. Browser diagnostics omit the signed wall stamp and per-command vehicle receive time, so the export alone cannot reconstruct one-way command latency.
