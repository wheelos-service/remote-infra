## Acceptance criteria

Interpret the requested **30 fps** as a target for each of left, center and right while all three are displayed together. Interpret **one second** as the maximum camera capture-to-display age during control. Also measure input-to-matching receiver feedback and operator takeover-to-confirmed REMOTE separately. Record cold join, first frame and handback durations separately from steady-state response. Receiver acceptance alone cannot establish physical application.

Proposed repeatable nominal LAN test: warm up for 30 seconds, then run 10 minutes with all three cameras and an active test control session. Configure and verify 30 fps source cadence. Count distinct frames actually presented per camera in 10-second windows, including zero-frame windows. Use ≥29.5 fps per camera in every window as the proposed measurement tolerance. Report per-camera FPS, freeze count, longest gap, and p50/p95/p99/max age. Preserve raw counts and elapsed times for comparison. In every control-enabled interval, the conservative age of the **currently displayed** frame, including clock uncertainty and time since the last frame, must stay ≤1,000 ms on every required camera. Unknown timing or a breach must inhibit driving by that deadline, including during a freeze. A single violation fails the nominal run regardless of percentiles.

Measure input-to-feedback with the browser's monotonic clock and matching session/revision/sequence. Report misses separately from latency percentiles. Require matched feedback within one second for the nominal bench actions and apply any tighter active policy first. Exercise degraded links separately and judge them on timely inhibition, hold, lock and safe recovery. Retain the current default 50 ms command period, 300 ms pause and 1,500 ms terminal lock. [Control timing](../frontend/src/lib/control-timing.ts)

## Work sequence

1. **Establish the comparison.** Record remote-infra, Apollo and SDK-Kit revisions, deployed image IDs, browser build, display refresh, camera mode, resolution, bitrate, GOP and selected ICE path. Use identical settings and the same three feeds for reference and candidate. Capture per-camera source frames, encoder output, worker queue depth/drops, WebRTC receive/decode/presentation counts, and browser callback gaps. Correlate with control sequence, receiver feedback and chassis/Guardian transitions. Export bounded, credential-free diagnostics. Reproduce the reported reference success through acquire, takeover, release and reacquire.
2. **Port the native handback contract selectively.** Reference commit `8b594bd` adds an authenticated device context POST with a three-second Redis capability marker and native revocation/handback reporting. Verify the paired Apollo receiver advertises capability only in supported Cyber mode. Keep older GET-only receivers observation-capable. Require fresh capability and authorized v2 identity for managed Cyber admission. Keep v1 timing-policy responses and its explicitly configured simulation path. Bind native ACKs to the authenticated vehicle and pending session/revision. Release the fence only after revocation is applied and the vehicle confirms exit from REMOTE. From `cda8950`, adopt scoped blocker diagnostics for active owner, pending handback and receiver unavailable. Bound legacy reservation lookup and keep it outside the command path. Preserve tenant/vehicle ACLs, single ownership, signatures and replay checks.
3. **Prove video age before enabling driving.** Map each presented frame to its source timestamp and bound clock error. Validate the mapping against an independently filmed timecode or light transition on the target workstation. The documented appsink timestamp omits upstream camera buffering, so measure or bound that delay as well. Test reconnects, timestamp resets, rollover, duplicate frames, missing metadata and frozen tabs. If browser capture metadata lacks a verified mapping, correlate a source frame ID/timestamp with its RTP frame. Keep observation available while evidence is missing. Replace the global UI gate only after proving a per-camera, per-session freshness decision that expires even without another callback. Reset it on track replacement and require fresh frames on all three cameras plus explicit re-arm after a pause. Enforce deployment eligibility at the Gateway for clients that bypass the workbench.
4. **Tune the measured bottleneck.** If source cadence is low, inspect camera negotiation and hardware encoder throughput with all three streams enabled. If age grows before publish, cap time in queues and recover a decodable stream at the next keyframe after dropping stale H.264 data. If transport dominates, sweep aggregate bitrate against measured link capacity at fixed FPS and resolution first. Test one-camera keyframe recovery under loss. If decode or display dominates, profile the target browser with three hardware-decoded tracks and aggregate diagnostics outside per-frame rendering. Change one variable at a time and retain it only when matched traces improve the limiting stage without regressing another camera or control feedback.
5. **Exercise control under media load.** Keep the existing lossy signed command path independent of reliable feedback and HTTP lease renewal. Measure signing/send delay, sequence gaps and feedback age while the cameras saturate the test link. Test brief RTC loss, prolonged loss, stalled single camera, Gateway outage, lease expiry, replay, delayed ACK, browser exit and manual override. Verify neutral/brake-only recovery, explicit operator re-arm, emergency brake availability and terminal locking. A stale ACK, resumed video or reconnect must never restore an old driving input. Verify which tile reports a stall, that one stale feed inhibits driving by the one-second deadline, and that repeated recoveries neither rebuild healthy tracks nor automatically re-arm control. Keep the replay deterministic using relative timings. Use real browser measurements for the 30 fps acceptance run.

**Test deployment on `zj@10.0.39.120`.** After local green, reserve an idle bench window. Record the current image IDs, saved LAN configuration and rollback revision. Record selected ICE path and repeat on each transport intended for deployment. Pass only when the nominal metrics and every degraded-state transition above hold. On failure, stop the trial, confirm safe control release locally at the bench, restore prior images/configuration and verify observation and lease state before another run.

During the bench run, start browser, LiveKit and Gateway capture together. Record build, vehicle, observer/track identity, clock origin and run window. Collect one-second deltas for inbound packets lost, jitter-buffer delay per emitted frame, frames received/decoded/dropped and distinct frames presented per camera. At the first 503 or pending banner, capture its exact text, timestamp, route, HTTP result, reason code and request ID, then correlate with the audit and that vehicle's lease/handover revision at that instant.
