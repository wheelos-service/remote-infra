# Release capabilities and limitations

The supported deployment is one Docker Compose host with the React frontend,
Go Gateway, Casdoor, PostgreSQL, Redis, LiveKit, and Caddy. The AMD64 bundle
includes compiled applications and runtime dependencies for an x86_64 Linux
Docker host; the release was built and exercised on Ubuntu 22.04.

## Supported workflow

- Deploy without a domain, using a stable LAN address and a trusted local CA.
- Sign in through Casdoor; manage organizations, invitations, vehicle enrollment,
  and fixed roles through the dashboard.
- Observe active vehicles in the signed-in organization and view their media
  when compatible vehicle software publishes it.
- Use the same console and API from the host and other LAN computers.

The release starts with an empty fleet and generated per-installation
credentials. It does not include or configure vehicle software. Initial browser
login tokens and login cookies are configured for seven days; deployment startup
reconciles that setting. Vehicle and control-session credentials have separate
lifetimes.

## Current limits

- **Managed native driving is disabled.** Non-allowlisted control acquisition
  returns HTTP 503 before creating authority. Supported v2 simulation control
  requires an explicit disposable-simulator allowlist; the release defaults to
  an empty list. Never put a physical vehicle in that list to bypass the gate.
- Task dispatch and event acknowledgement are unavailable in managed mode.
  Read-only fleet/operational views do not imply those actions are enabled.
- Permission changes take effect in stored authorization, but existing media
  cleanup is best effort. An administration response does not prove immediate
  participant eviction or physical handover.
- The retained legacy video-session API has weaker ownership checks than the
  current viewing API. Legacy session IDs are not an isolation boundary;
  use the primary frontend and do not rely on the legacy API for user isolation.
- SQLite operational history has a single Gateway owner. Multi-host scaling
  and automatic record rotation are outside this release.
- Server verification does not test real vehicle cameras, actuators, or safety.
  Vehicle integration and physical driving validation are separate work.

## Components and protocol compatibility

`frontend/` and `teleop-gateway/` are the primary browser/server pair.
`packages/teleop-shared/` provides shared input and view state machines.
Vehicle SDK builds and Apollo configuration are managed separately from this
server repository.

Current payload schemas are in [api/schemas](../api/schemas/). V2 control must
not silently downgrade to v1. Viewing leases grant observation only; control
leases and handover remain separate. Browser feedback, Cyber publication,
and simulation acknowledgements do not establish physical actuation or stop.

The supported deployment is generated by `infra/scripts/deploy.py` in the
private state directory. Root-level compatibility Compose files and the
legacy operator console have been removed; do not use or recreate a parallel
deployment path.
