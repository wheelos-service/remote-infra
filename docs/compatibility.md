# Release capabilities and limitations

The supported deployment is one Docker Compose host with the React frontend,
Go Gateway, Casdoor, PostgreSQL, Redis, LiveKit, and Caddy. The AMD64 bundle
includes compiled applications and runtime dependencies for an x86_64 Linux
Docker host. The release was built and tested on Ubuntu 24.04.

## Supported workflow

- Deploy without a domain, using a stable LAN address and a trusted local CA.
- Sign in through Casdoor; manage organizations, invitations, vehicle enrollment,
  and fixed roles through the dashboard.
- Observe active vehicles in the signed-in organization and view their media
  when compatible vehicle software publishes it.
- Request native control for an active vehicle within the remote operator's
  assigned scope. Current and newly enrolled vehicles qualify automatically.
- Use the same console and API from the host and other LAN computers.

The release starts with an empty fleet and generated per-installation
credentials. It does not include or configure vehicle software. Initial browser
login tokens and login cookies are configured for seven days; deployment startup
reconciles that setting. Vehicle and control-session credentials have separate
lifetimes.

## Current limits

- Native acquisition requires a current instance-bound receiver heartbeat.
  The workbench enables control requests after verifying source freshness on
  all three front cameras. An incomplete handover blocks another session.
- Simulated control uses an explicit list of disposable simulators, empty by
  default. Its acknowledgements apply only to simulation sessions.
- Task dispatch and event acknowledgement are unavailable in managed mode.
  Read-only fleet/operational views do not imply those actions are enabled.
- Permission changes take effect in stored authorization, but existing media
  cleanup is best effort. An administration response does not prove immediate
  participant eviction or physical handover.
- Removing a cached vehicle media token does not revoke a previously issued
  LiveKit JWT. Maintenance and permission changes must honor the recorded token
  expiry and room-drain checks.
- SQLite operational history has a single Gateway owner. Multi-host scaling
  and automatic record rotation are outside this release.
- Server verification does not test real vehicle cameras, actuators, or safety.
  Vehicle integration and physical driving validation are separate work.

## Components and protocol compatibility

`frontend/` and `teleop-gateway/` are the primary browser/server pair.
`packages/teleop-shared/` provides shared input and view state machines.
Vehicle SDK builds and Apollo configuration are managed separately from this
server repository.

Current payload schemas are in [api/schemas](../api/schemas/). The control packet is
named `vehicle-control.schema.json`; its payload remains wire version 2 and must
not silently downgrade to v1. Viewing leases grant observation only; control
leases and handover remain separate. Browser feedback, Cyber publication,
and simulation acknowledgements do not establish physical actuation or stop.

The supported deployment is generated by `infra/scripts/deploy.py` in the
private state directory. Root-level compatibility Compose files and the
legacy operator console have been removed; do not use or recreate a parallel
deployment path.

### Native control and source-video verification

The managed Gateway evaluates the active enrollment and operator grant on each
request. An operator with organization-wide control scope can access vehicles
enrolled after sign-in. Selected-vehicle grants retain their assigned scope.
The original 1.1.3 image required a native bench list. On upgrade, existing
entries and empty or absent lists require no migration or per-vehicle edits.
The percent-command receiver polls the instance-bound native-v3 context,
accepts signed v2 packets, and reports native handback for the same revision.

#### Handheld gears and service brake

The browser enables handheld driving after the bound receiver returns reliable
`READY` feedback with reason `awaiting_command_gear_v1`. Older receivers
retain standby, takeover, release and emergency-stop controls. The Apollo
source changes are in commit `88c06171a62510571acf41b40bf66eb99341ed85`
on `teleop-V1` and cover Teleop, Guardian and Canbus together. This branch
reports `COMPLETE_AUTO_DRIVE` for both local automation and remote driving.
The dashboard confirms takeover from fresh Guardian `REMOTE` and an engaged
chassis mode in the same vehicle state report.
[Native patch against Apollo 6de50aa262](../infra/apollo/handheld-gear.patch)

The four required signed v2 command values are `steering, throttle, brake,
direction`. The Ed25519 signature covers the UTF-8 JSON array of version, type,
vehicle ID, session ID, client instance ID, receiver instance ID, revision,
sequence, timestamp and those four integers, in that order. The two optional
extensions are mutually exclusive.

| Input | Signed extension after the four integers | Receiver behavior |
| --- | --- | --- |
| LT gear cycle (N → D → R → N) | Append the value of `gear_request` as a JSON string, e.g. `"R"` | One request with steering, throttle and direction zero and brake 20%. A fresh known chassis gear, speed at or below 0.1 m/s in magnitude and the Guardian brake interlock permit the shift. |
| Service brake | Append JSON boolean `true` for `service_brake: true` | Apply the requested 1–100% service brake with zero throttle and direction. Steering remains proportional. |
| Other commands | End the array after direction | Idle, heartbeats, steering and propulsion leave gear selection alone. The existing emergency-stop command uses 100% brake, zero throttle and zero direction. |

Throttle requires D or R in a chassis sample less than 500 ms old. The
direction field on propulsion identifies that confirmed gear. A request for
another gear blocks propulsion until the chassis reports the requested gear.
A lost or interlocked shift allows service braking and a fresh button press
after releasing LT and recentering. The panel shows the last
request and the fresh chassis gear separately. [Command schema](../api/schemas/vehicle-control.schema.json)

The matching SDK-Kit generated publisher schedules 640 × 480 test images at
30 fps and encodes its camera index, Gateway clock epoch, capture-time lower
bound and CRC-16 in the top 16 rows. Physical cameras can carry their capture
stamps in LiveKit frame metadata matched by RTP timestamp. The browser samples
the same authenticated monotonic clock and accounts for the request interval.
Clock estimates expire after 15 seconds and allow 1000
ppm drift plus timer resolution. All three stamped feeds must stay fresh for
one second before driving becomes available. A held image expires at its
individual source-age deadline. Camera feeds without verified capture stamps
remain available for observation.
