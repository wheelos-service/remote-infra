# 人员、组织与车辆认证授权建设方案

> 状态：目标设计与分阶段实施建议，不代表以下能力已经实现。
> 当前实现和配置见 [authentication.md](authentication.md)；
> 兼容约束见 [compatibility.md](compatibility.md)；
> 路由/action、生命周期与排障验收见 [authorization-contract.md](authorization-contract.md)。

## 1. 核心原则：认证与授权职责分明

**Casdoor 负责认证；Gateway 对业务授权负责，内嵌 Casbin 作为统一策略引擎；
Control Lease 独立裁决实时控制权。**

认证回答“请求者是谁、凭证是否可信”；业务授权回答“该主体当前能否对指定组织、
指定车辆执行指定操作”。成功登录、持有某个 JWT Scope、进入 LiveKit 房间，
都不等于获得对应车辆的业务权限或实际控制权。

| 组件 | 应负责 | 不应负责 |
| --- | --- | --- |
| Casdoor | 人员账号、登录、SSO、可用的 MFA；OAuth 客户端、凭证管理及令牌签发 | WheelOS 企业组织归属、车辆范围、控制权和任务权限的最终裁决 |
| Gateway 令牌验证层 | 校验受信任的 issuer、签名、audience、有效期及令牌契约，提取可信主体信息 | 根据前端传入的 issuer 动态信任任意身份源；将登录成功直接视为业务放行 |
| WheelOS Backend / Gateway | 管理业务 API、主体绑定、人员/组织/车辆状态、邀请与凭据发放编排、受控策略管理、审计 | 重新实现密码登录或 OAuth 服务；再建一套与 Casbin 双向同步的 RBAC/ACL |
| Gateway / PEP | 验证令牌及 Scope、查询可信资源归属和状态、调用 Casbin、执行每个 API 的授权结果 | 信任客户端自报组织；以 Enforce 允许代替 Lease 或车端安全校验 |
| 内嵌 Casbin | 组织内角色关系、角色操作权限、车辆范围策略及 Enforce | 账号认证、邀请生命周期、业务资源状态、控制会话和凭据保管 |
| Gateway Control Lease + Redis | 原子维护有效 Lease、revision、控制互斥、续租和交接栅栏 | 成为人员、组织和长期权限的主数据库；单独承担命令防重放 |
| LiveKit | 执行 Gateway 下发的房间和媒体/DataChannel 传输权限 | 裁决成员关系、车辆归属或物理控制权 |
| 车端 | 使用独立机器身份接入；校验控制上下文、签名、序号、期限和本地安全条件 | 根据消息中的 vehicle_id 或自报身份直接接受控制 |
| 前端 | 登录、组织选择、展示服务端返回的可用操作及拒绝原因 | 作为最终授权边界；持有设备凭据或 LiveKit API Secret |

统一的是认证入口、主体解析、授权接口和审计规则，而不是让人员与车辆共用客户端、
密钥、登录方式或全能令牌。

### 1.1 总体架构审查结论与部署边界

采用 **Casdoor + WheelOS Gateway 内嵌 Go Casbin + PostgreSQL** 作为目标架构，
保留现有 Redis 控制权与 SQLite 运营存储。该架构符合统一入口、授权单一事实来源、
最少部署组件的目标；以下是模块关系，不代表新增多个后端服务：

```text
人员浏览器 -- Authorization Code + PKCE --> Casdoor
车辆客户端 -- 独立 Client Credentials ---> Casdoor
                         |
                    Access Token
                         v
WheelOS Backend / Gateway（一个后端部署单元）
  管理 API：人员邀请、组织、车辆、受控权限配置
  PEP：JWT/Scope -> 主体与资源状态/归属 -> 内嵌 Casbin -> 业务执行
  凭据发放编排：通过受限 Management API 对接 Casdoor
  Control Lease：申请/续租/释放、revision、交接状态机
       |                    |                     |
       v                    v                     v
  PostgreSQL             Redis                 LiveKit
  业务生命周期           有效 Lease            短期房间令牌
  Casbin 策略            控制互斥/栅栏          媒体与数据传输
  审计/版本/outbox

车端：机器身份绑定 + 控制上下文/签名/序号/期限/本地安全条件校验
现有 SQLite OperationsStore：继续承担运营数据/任务/事件
```

WheelOS Admin 是管理界面，复用同一后端的受控 API，不是独立授权服务。
Casbin 是 Go 进程内依赖，其 Management/RBAC API 不直接暴露给浏览器。
PostgreSQL Adapter 是策略持久化层，不负责给管理请求鉴权。
Casdoor 的账号邀请能力和 WheelOS 的组织加入授权不是同一件事：前者需实测支持，
后者由 Gateway 编排、绑定并审计，不因 Casdoor 账号创建成功自动授予成员权限。

不新增独立 RBAC/ACL 服务、第二套授权关系表、Device ID、资源权限图数据库或另一个 IdP。
Lease/revision 防止过期控制者继续持权，车端签名、sequence、时间和会话校验负责命令真实性
与防重放；这两类责任不能合并成“Lease 自动保证所有命令安全”。

### 1.2 目标操作体验：录入人员和车辆，再分配权限

平台运维先完成一次性初始化：受信任 Casdoor、浏览器 OAuth 客户端、受限管理凭据、
数据库迁移、密钥存储与交付设施、初始组织和平台管理员。公共服务参数不由每个业务管理员重复配置。

| 业务管理员操作 | 系统自动完成 | 完成条件 |
| --- | --- | --- |
| 录入/邀请人员，选择组织 | 创建或关联 Casdoor 账号流程、生成组织邀请、登录后绑定可信主体 | 邀请已接受且身份已绑定；待接受人员无业务权限 |
| 录入车辆，选择所属组织 | 保留 vehicle_id、幂等发放独立机器客户端、验证主体绑定、生成受保护配置 | 凭据已安全安装，车端认证自检通过 |
| 为人员选择角色和车辆范围 | 校验管理员可授予边界，将角色及范围写入 Casbin，提交版本/审计事件并同步策略 | 人员/组织/车辆有效，策略已生效；撤销另显示会话清退状态 |

日常管理员不编辑 JSON/CSV/Model，不手工同步 subject 映射，不逐车复制平台公共参数，
不在 Casdoor 与 WheelOS 两处重复配置车辆权限。人员接受邀请并正常登录；
受控部署工具或授权安装人员仍需把每车凭据安全安装到对应车辆，这不是可省略的信任步骤。
不要求额外的车辆激活码流程，不等于无需验证凭据归属和安装结果。

人员状态、车辆接入状态、权限生效状态分别展示。邀请未接受、凭据发放失败、
主体待核验、策略未同步均显示具体阶段和可重试操作，不能统一显示“鉴权完成”。
认证通过只代表可接入，不代表视频就绪、持有控制权或已获准真实驾驶。
Casdoor 自动化能力未验证前只能交付显式的受控人工过渡流程，
不能宣称已经达到“只录入和分配”的最终体验。

## 2. 身份、Scope、业务权限与控制权

### 2.1 主体绑定

- 人员：经过验证的 `(issuer, sub)` 绑定 WheelOS 内部 `user_id`。
- 车辆：经过验证的机器主体绑定不可变的 `vehicle_id`；认证绑定可以有版本。
- 人员与车辆必须有明确且不可混用的主体类型，不以请求路径或自报字段决定身份类型。
- 不假定车辆 `sub == client_id`；必须根据实际 Casdoor 令牌契约确认稳定主体。
- 不因邮箱相同自动合并人员，不因未知 subject 自动创建已授权业务主体。
- WheelOS 组织来自业务数据库，Casdoor Organization 不自动等同于客户组织。

首期保留单个配置受信任 issuer，不为未来扩展提前建设多 IdP 平台。令牌验证层应保留
issuer/sub，不能只保留一个丢失身份来源的显示名称。

### 2.2 四层判断

1. **认证有效**：令牌来自已配置的身份源，符合签名、audience、有效期及 Access Token 契约。
2. **API 委托范围有效**：Scope 允许调用相应类别 API，但 Scope 不授予具体组织或车辆。
3. **业务权限有效**：内部主体、成员关系、角色、车辆范围和资源状态全部允许本次操作。
4. **执行授权有效**：控制操作还需有效 Lease、revision、车端校验及安全条件。

不能把任何一层当成其他层的替代品。ID Token 不应替代 API Access Token；
具体可验证的令牌类型字段必须以当前 Casdoor 版本为准，不虚构 claim。

当前兼容 Scope 为 `teleop:observe`、`teleop:control`、`teleop:vehicle`。
目标业务权限如 `vehicle.read`、`camera.live.view`、`remote_control.request` 由 Gateway
维护，不能直接把两组字符串互相替换。细分车端 Scope 前需同时更新 Casdoor、
Gateway 路由规则、C++ 请求和测试，明确默认 Scope/显式申请行为。

### 2.3 组织角色建议

| 角色 | 首期建议能力 | 默认不包含 |
| --- | --- | --- |
| org_admin | 本组织成员、车辆登记、授权管理及必要查询 | 远程控制、物理维护执行、跨组织人员禁用 |
| remote_operator | 授权车辆状态、视频、申请控制 | 成员管理、车辆转组织、凭据管理 |
| viewer | 授权车辆只读状态和视频 | 告警确认、创建任务、控制 |
| maintainer | 授权车辆健康、诊断和明确开放的维护操作 | 控制、成员管理 |
| dispatcher | 授权车辆及已经实现的任务能力 | 默认控制资格、尚未实现的调度/执行接口 |

所有角色共享同一份权限定义和测试。车辆范围为 `all` 或 `selected`，
仅在当前组织内有效；选择车辆或组织不会产生新授权。

首期一个成员一个主角色可以保留，但必须接受其限制：若需要“组织管理员兼驾驶员”，
不能为方便直接把控制权并入 org_admin。应在后续显式扩展角色组合，或先保持职责分离。
权限管理能力不是任意授权能力；可分配的角色需有服务端定义的边界，禁止自我提权。

### 2.4 Casbin 模型契约

- Domain 为内部 org_id；人员 Subject 使用 `user:<user_id>`，角色使用
  `role:<role_name>`，禁止用户与角色字符串混淆。车端不复用人员角色体系。
- 首期固定角色能力，管理员只分配组织内角色及 `all/selected` 车辆范围；
  暂不开放自定义 Model、任意策略直授、任意角色继承。
- 车辆操作须同时满足“有效成员 + 角色允许 action + 同组织资源 + 车辆在授权范围”。
  Casbin 承担角色与范围匹配，Gateway 承担可信主体、成员/资源状态和归属前置检查。
- 范围绑定到本次角色分配，避免角色组合时交叉扩大权限；首期一个主角色。
  `all` 仅表示该组织当前及后续纳入的有效车辆；`selected` 不自动包含新车。
  不用组织角色的 `*` 许可绕过 selected，也不以用户直授绕过角色能力。
- 单车资源由 Gateway 根据 vehicle_id 查出真实 org_id；请求组织只作上下文并需比对。
  组织列表请求先验证成员与查询权限；车辆范围过滤须发生在分页、计数和聚合之前。
- 成员管理、车辆登记等无现有单车对象的 action 使用明确的组织资源，
  不伪造 vehicle_id；平台引导权限与普通组织域隔离。
- 策略缺失、模型/策略加载失败、授权调用出错或无法确认版本新鲜度时不放行，
  记录可诊断原因；依赖故障不能伪装成正常的空权限结果。

以上是必须满足的授权语义，不是已经验证的 Casbin Model。P0 使用实际选定的 Go Casbin
和 PostgreSQL Adapter 验证角色与范围的 AND 关系、域隔离、错误处理及事务接口，
形成可执行模型和反例测试后，才接入业务路由。

## 3. 请求流程

### 3.1 人员访问

1. 浏览器通过 Authorization Code + PKCE S256 登录 Casdoor。
2. Gateway 验证 Access Token，解析可信 issuer/sub，查找内部人员绑定。
3. 返回内部人员状态及有效组织成员关系；未绑定人员只能进入受控邀请绑定流程。
4. 浏览器在每次组织相关请求中携带显式组织上下文。
5. Gateway 校验人员、组织和成员状态及资源归属，通过内嵌 Casbin 判断 action 与车辆范围。
6. 列表在数据库查询阶段过滤；详情和写操作再次执行对象级授权。
7. 允许后执行业务操作，记录必要的结果审计。

前端切换组织不能改变其他标签页的隐式全局组织。已有控制会话固定绑定创建时的组织、
人员和车辆，不因 UI 切换组织而重新解释身份。

现有 `/api/auth/me` 返回 `Name/Roles/Organization`，车端诊断也依赖此契约。
建议新增明确版本的业务身份响应，或采用先增后迁的兼容方式，避免一次替换所有消费者。
业务组织列表不再从 JWT 的 tenant/organization claim 直接构造。

### 3.2 车辆访问

1. 每辆车使用独立 client credentials 获取短期 Access Token。
2. Gateway 验证令牌及设备类别 Scope，解析已注册的机器绑定。
3. 校验绑定、车辆、组织和 provisioning 状态。
4. 强制请求路径和数据中的 vehicle_id 与绑定车辆一致。
5. 对遥测、健康、媒体需求、房间令牌和控制上下文分别判断具体能力。

待分配组织、provisioning 未完成或被禁用的车辆不获得普通业务能力。
但禁用后的控制撤销上下文与必要交接确认必须有受限的安全收尾路径，不能误授新控制权，
也不能因全面拒绝设备请求而阻断已有控制的撤销。

### 3.3 控制与视频

- 视频：先检查 `camera.live.view` 和车辆范围，再签发指定房间的短期订阅令牌。
- 控制：先检查 `remote_control.request`，再由 Redis 原子裁决有效控制会话。
- 保持单车单控制者及当前单操作员控制约束；组织切换不能被用来绕开操作员互斥。
- 车辆仍需要订阅控制数据并发布监控数据，不能照搬“车辆只有视频 Publish”的简化配置。
- 当前 C++ 控制是显式模拟模式；不能通过本方案新增真实底盘执行或宣称实车认证完成。

## 4. 存储与模型调整

### 4.1 存储真相源

| 存储 | 首期职责 |
| --- | --- |
| PostgreSQL 业务数据 | 内部主体/外部身份绑定、组织、成员生命周期状态、车辆、认证绑定、邀请、provisioning、授权版本/outbox 和业务审计 |
| PostgreSQL Casbin Adapter | 唯一的人员组织角色关系、角色操作权限与车辆范围策略 |
| Redis | 有效控制 Lease、revision、交接栅栏、已有实时协调与最新状态 |
| 现有 SQLite OperationsStore | 保留当前运营数据/任务/事件接口，不在本轮顺带迁移 |

PostgreSQL 可以记录控制历史，但不能与 Redis 同时裁决实时控制权。
未来迁移运营存储应独立设计，不复制一套相同的任务/事件服务。
Casdoor 是人员账号目录的事实来源，WheelOS 只保存业务绑定和必要状态，不复制密码或账号体系。
成员生命周期记录只表达加入、暂停、离开等业务事实，不重复保存角色或授权车辆集合。
不另建 `user_roles`、`vehicle_acl` 再与 Casbin 双向同步；派生读模型不得成为第二个授权源。

### 4.2 模型约束

- 保留现有 vehicle_id 作为不可变接入标识，继续用于 URL、消息、房间及 Redis key。
  内部 UUID 可另设，vehicle_code/name 可变但不能改变接入身份。
- 外部人员身份对 `(issuer, subject)` 唯一；机器主体不能映射到多车，
  同一可信主体不能同时被解释为人员与车辆。
- 车辆认证绑定独立记录版本、issuer、client_id、subject、状态及 secret_reference；
  这是车辆的认证记录，不引入独立 Device 业务对象。
- 业务成员与车辆使用组织约束；Casbin 通用策略表不能假定有业务外键保护，
  所有策略写入必须校验主体、组织、车辆和 action，并处理删除/转组织后的失效策略。
  即使残留旧策略，Gateway 的成员状态和资源归属检查也不能被绕过。
- 人员全局禁用仅由受控平台权限执行；组织管理员只能暂停/移除本组织成员。
- 防止移除最后一个有效组织管理员；首次平台管理员通过受控引导过程建立，
  不开放公共“首个登录者成为管理员”。
- 邀请使用短时单次凭证、摘要存储、明确目标和绑定审计；定义过期、冲突与重试行为。

## 5. 权限撤销与跨系统一致性

“立即生效”需要分层定义，不能只写成清理缓存：

1. 将主体/成员/资源状态或策略变更、授权版本及撤销 outbox 原子持久化。
   必须核验所选 Adapter 能否参与同一数据库事务；不能假定一次 Casbin API 调用
   会同时更新业务表、审计和事件。事务失败不得发布可用的新内存策略。
2. 提交后开始授权检查的新请求不得读取过期许可。Casbin Enforcer 的内存策略本身
   就是副本，采用 Watcher/通知并不能独立保证撤销一致性。实例须校验权威版本，
   落后时加载对应一致快照并原子替换；无法证明策略新鲜则拒绝业务。
   通知只用于加速，另有漏通知、重启和加载失败后的对账恢复。
   数据库不可用不能回退旧 JSON 或未经确认的旧 Enforcer；首期不加额外正向许可缓存。
3. 已受理的高风险操作需定义授权版本校验点；控制 acquire/renew 必须覆盖
   数据库撤销与 Redis 写入之间的并发窗口，不能仅靠异步 worker 保证安全。
4. 幂等处理 outbox，撤销相关控制/观看会话并处理已有 LiveKit participant。
   记录待处理、重试、完成和超时状态，防止进程重启丢失撤销。
5. 控制撤销进入现有交接状态机，保留 `PENDING`、revision 和设备确认；
   不通过删除栅栏、删库或旧备份恢复来强制解锁。
6. 保留经过严格限制的原会话安全释放与设备确认路径；不能让权限变更阻止安全收尾。

HTTP 请求拒绝、车端停止接受命令、媒体连接关闭是三个不同完成条件。
具体上限应根据轮询周期、请求超时、Lease 和 LiveKit 行为确定并写入验收；
异步故障未收敛时应显示“撤销处理中/失败”，不得显示全部完成。

移除 participant 也不必然使已签发房间 JWT 永久不能重连。必须验证当前 LiveKit
版本的权限更新、移除与重连语义，并结合短期 token、会话级身份/版本及再次准入策略，
验证旧 token 不能重新获得已撤销的访问权。

车辆转组织必须在停止新增授权、撤销相关会话并完成必要交接后进行。
历史记录是否归旧组织、是否随车转移另立明确数据策略，不按当前 org_id 无条件搬移可见性。

## 6. 车辆自动发放与凭据生命周期

目标体验为“一次登记车辆，后台自动准备身份和配置”，不是“无审核获得业务权限”。

- 先创建车辆业务记录和幂等 operation_id，再执行外部 provisioning。
- Casdoor 创建成功、超时未知、数据库失败必须可核验和恢复；未知结果先对账，
  不盲目重复创建客户端。
- 令牌实际签发与验证通过后才确认 subject 映射可用，不根据名称猜测。
- secret 保存于受控加密存储或 Secret Manager，普通业务表只存引用。
- 通过短时单次领取的受控交付流程下发配置；定义响应丢失、重复领取和配置丢失的恢复方式。
- 不在普通详情页展示 secret；不进入前端静态配置、URL、日志、Git 或命令行。
- 轮换是否支持双密钥重叠必须验证实际 Casdoor 能力；不支持时采用明确维护窗口，
  或经过设计的版本化客户端切换，不能假装旧、新凭据可同时有效。
- 更改 secret 不等于撤销已签发 JWT；Gateway 必须检查机器绑定状态。
  同主体密钥轮换后的旧/新 JWT 若不可区分，应明确残余有效期或采用可区分的绑定版本方案。
- 普通密钥轮换不改变 vehicle_id，不重新创建车辆业务对象。

不重新实现认证服务，也不在未知 Casdoor API 的基础上承诺全自动化。
生产 Casdoor 版本、Management API、最小管理凭据、Scope、subject 和轮换能力
均先在隔离环境验证；缺少能力时保留受控人工 provisioning 作为显式交付状态。

## 7. 配置简化与诊断

管理员最终只需维护业务组织、成员角色/范围和车辆登记；IdP 公共参数由平台配置一次，
每车独立凭据由发放流程产生，不能通过车队共享密钥简化。

当前统一策略文件是静态授权过渡方案，不是已完成的多租户数据库。
迁移工具必须同时支持该文件和旧三份 JSON，以显式选择的单一来源导入，
不能合并来源或在运行时覆盖数据库权限。

现有 `vehicle_auth_check` 验证受保护配置、OAuth/Gateway、subject 映射与
LiveKit token 签发。后续建议补充结构化阶段、request_id、稳定错误码和管理员可见的
脱敏认证状态；媒体网络、相机、Cyber、控制就绪仍是独立检查，不能将认证成功标为车辆可驾驶。

建议错误分类为：配置错误、身份无效、主体未绑定、主体禁用、成员无效、
权限不足、跨组织拒绝、控制冲突、依赖不可用；服务端记录原因，外部错误响应避免泄露其他租户信息。
通常身份无效返回 401，业务拒绝返回 403，资源隐藏策略可使用 404，
控制冲突返回 409，已识别的关键依赖故障返回 503，并统一 request_id。

### 7.1 高效操作与快速定位的交付要求

- 角色使用固定模板、默认当前组织，支持受控批量选择车辆；提交前明确展示 all 会覆盖本组织后续新增车辆。
- 本地校验、登记和策略事务优先同步完成；调用 Casdoor、凭据发放/交付等跨系统长操作
  以持久 operation_id 异步编排。刷新页面、重试或丢失响应不得重复创建身份或扩大授权。
- Casdoor Management API 不进入普通业务请求的逐请求路径；普通请求依赖 JWT 验证、
  权威业务状态和足够新的策略。JWKS 缓存与 OAuth 令牌刷新仍按认证契约执行。
- 每次 HTTP 往返使用独立 request_id，后台任务跨重试沿用 operation_id；
  稳定错误码不从异常文本推断，记录阶段、耗时、最近成功/失败时间、是否可重试及处理责任。
- 管理界面分别展示身份、业务权限、策略生效、控制权和媒体/车端状态，
  不以单一绿灯掩盖待接受邀请、待安装配置、策略落后或安全交接未完成。
- 业务管理员可看本组织脱敏状态，平台运维可按关联 ID 查详细阶段，
  车端只看本车；诊断不能成为越权查询或输出令牌/凭据的旁路。

现有认证与设备检查边界的 request_id、稳定错误码和兼容响应契约见
[authentication.md](authentication.md)。全局错误统一、持久异步编排、
策略版本状态和管理诊断界面仍需按下列阶段交付，不能因局部自检可用就视为完成。

## 8. 实施顺序与验收

近期快速交付的 M0–M5、试点边界及演进触发条件统一记录在
[管理闭环实施计划](../.agents/auth-management-plan.md)。
先复用现有 HTTPS 监控、按需媒体、Redis Lease 和模拟驾驶链路，
不以新增车辆 WSS、API Key 或迁移运营数据库作为前置条件。
下表保留完整目标的验收要求；人工预配身份的试点不等于完成自动邀请、
凭据交付和在线撤销。

| 阶段 | 交付物 | 验收门槛 |
| --- | --- | --- |
| P0 契约与能力核验 | 路由/action/资源矩阵、固定角色与范围；实际 Go Casbin 模型、Adapter 事务和隔离 Casdoor 验证记录 | 角色与范围必须同时满足；无虚构 API/claim；明确自动发放能力及撤销指标 |
| P1 数据与引擎基础 | PostgreSQL 迁移、主体/成员生命周期、Casbin Adapter、受控策略写入、邀请与平台初始化 | 授权关系唯一；域隔离、主体冲突、跨组织范围、事务回滚和默认拒绝测试通过 |
| P2 迁移与统一授权 | Gateway PEP 统一入口、单一可选授权源、导入 dry-run、影子对比、版本化身份响应 | 列表/详情/写入均受控；旧 admin 不直接成为新控制授权；显式保留旧 control 隐含 observe 语义 |
| P3 撤销闭环 | 策略版本/同步恢复、outbox、Lease/续租重检、并发屏障、安全收尾、LiveKit 撤销 | 漏通知、旧 Enforcer、重试/重启和依赖故障下不恢复旧权限；动态管理上线前完成 |
| P4 最小管理界面 | 人员邀请/组织、车辆、角色与范围三个管理入口；阶段状态、重试和基础审计 | 管理员不隐式获控制权；越权授予和最后管理员删除被拒绝；不要求用户编辑策略文件 |
| P5 自动 provisioning | 幂等创建、身份核验、受保护配置交付/安装衔接、轮换/吊销；复用车端自检 | 未知外部结果不重复创建；单车轮换不影响其他车；不手工同步主体映射 |
| P6 目标体验与受控切换 | 录入人员/车辆→分配角色范围的端到端验收、导入核对、回滚演练 | 一次平台初始化后不逐人逐车重复配置 IdP；失败可定位恢复；回滚不恢复撤销权限或控制栅栏 |

最初的 P0/P1 基础已交付；近期按 M0–M5 推进人工身份预配的单实例管理试点，
不迁移全部运营存储。试点优先验证登记、授权、监控及模拟驾驶，
自动邀请和凭据发放仍需外部能力核验。
这不缩减最终目标：只有人员邀请/绑定、车辆凭据安全交付、自检、
策略生效和撤销均串通后，才算实现“录入并分配即可完成接入授权”的操作体验。
基础审计随首次身份和策略写入交付，不能等管理报表或高级审计阶段再补。
迁移必须以旧授权的实际行为为准：observe/control 不一定能精确映射新角色，
无法无损表达的条目需要明确确认，不能为了导入成功附加任务、维护或管理权限。

至少覆盖以下跨组件验收：

- 一个用户属于两个组织，角色不同，跨组织访问和伪造组织上下文均被拒绝。
- viewer 不能申请控制，org_admin 不因管理身份获得控制权。
- remote_operator 的 selected 范围不会被组织角色通配策略扩大；
  移除角色后旧范围不能单独授权；新增车辆不自动进入 selected。
- 邀请待接受、主体待绑定、凭据待安装/核验及策略加载失败均不显示接入授权完成。
- 设备凭据不能冒用另一车辆；未绑定、禁用和过期身份被拒绝。
- 权限撤销与控制续租并发时，旧权限不能创建或延长有效控制权。
- 多实例漏通知或持有旧 Enforcer 时，新请求不能继续依据旧许可放行。
- 车辆禁用后业务请求被拒绝，安全撤销/交接仍能按状态机完成。
- 旧 LiveKit token 在撤销后不能恢复访问；异常时有可见的未收敛状态。
- provisioning 结果未知、交付响应丢失及重复操作可恢复且不泄密。
- 导入前后无非预期许可变化；回滚不会重新授权已禁用主体。

## 9. 合规边界

职责分离、最小权限、独立凭据、可审计变更和可验证撤销是工程控制措施，
不是法律合规或实车安全认证结论。正式部署还需按适用地区和业务场景明确
人员信息、视频/位置数据的处理依据、最小采集、保留/删除、访问审计、密钥管理、
跨境传输及事故响应要求，并由相应负责人确认。

默认部署不自动迁移，仍使用静态授权源；管理试点必须显式启用独立的数据库授权模式，
不得与旧授权配置混用或在故障时回退。试点不代表完成整套生产多租户鉴权。
权限变更事件写入成功也不代表已有控制/观看会话已撤销。
对外宣称“录入人员和车辆、分配权限即可完成”以前，仍须通过 P2–P6 的端到端验收。
