# Public-domain k3s deployment roadmap

Status: proposed future delivery target, not implemented or accepted.
Use when evaluating Kubernetes/k3s packaging, ingress, certificates, persistence
or media networking. Do not interpret this plan as permission to deploy the
retained manifests or enable native vehicle control.

## Current baseline

The supported release is single-host Docker Compose generated by
`infra/scripts/deploy.py`. Source deployment builds Gateway and Frontend.
The AMD64 bundle builds the same Dockerfiles and embeds the same deployment
script; the destination does not compile. Configuration, initialization,
registration and verification have one owner.

No Kubernetes manifests are maintained in this repository. This roadmap is a
future design target, not an executable deployment specification.

## Scope and invariant

k3s changes orchestration, not the authentication protocol:

- HTTPS, signed Ed25519 enrollment, administrator fingerprint approval,
  organization/vehicle binding and OAuth runtime authentication remain.
- Registration does not start a vehicle runtime.
- No implicit mTLS, systemd rollout or native-control enablement.
- Certificate infrastructure, vehicle admission and runtime authorization remain
  separate responsibilities.
- Keep public issuer URLs stable across migration; DNS migration alone does not
  migrate OAuth identities or database state.

## Target topology

```text
Public DNS -> Traefik Ingress TLS
  console domain -> Frontend
                 -> /api/* and /rtc* -> Gateway
  login domain   -> Casdoor

Gateway -> PostgreSQL / Redis / exclusive operational storage
Gateway -> LiveKit
Clients -> direct WebRTC TCP/UDP -> reachable LiveKit nodes
```

Preserve Gateway's gated RTC entrypoint; never replace it with a direct public
LiveKit signaling route just to simplify ingress. Ordinary HTTP ingress does
not transport WebRTC UDP or replace TURN.

## Single owners and configuration

- Choose one application delivery format: Helm or Kustomize.
- Use the same configuration contract as Compose. Public origins and issuer
  URLs have one authoritative input; generate dependent frontend/provider values.
- Convert installation initialization into an idempotent Job using existing
  business operations. Do not maintain another provisioning state machine.
- Prefer Traefik for ingress and cert-manager for ACME. Do not simultaneously
  retain Caddy ACME ownership for the same domains and ports.
- HTTP-01 works if the public challenge reaches ingress. DNS-01 is a separate
  option for inaccessible challenge ports/wildcards and needs scoped DNS API
  credentials. Cloudflare is optional.
- k3s default Traefik/ServiceLB occupies node ports 80/443; address conflicts
  before coexisting with a Compose/Caddy deployment.

## Persistence and replica constraints

- Start Gateway at one replica with exclusive persistent SQLite ownership.
  Use controlled Recreate/stop-write upgrades, not overlapping writers.
  A shared PVC or NFS does not make SQLite a multi-host database.
- PostgreSQL needs persistent storage, backups and tested restores, or an
  external managed service.
- Redis stores coordination/safety state, not disposable cache: preserve AOF,
  capacity and no-eviction requirements with an appropriate persistent setup.
- Persist Casdoor's data. Shared-provider databases and multi-replica operation
  require a deliberate migration and validation.
- Mount protected management/encryption credentials with file modes/ownership
  accepted by the application. Kubernetes defaults are not proof of compatibility.
- Restrict Secret RBAC and backups and enable suitable at-rest protection.
  Base64 is not encryption.

## LiveKit and TURN

Use the official LiveKit Helm chart as a reference, pin compatible versions,
and adapt it explicitly for k3s:

- host networking and normally one LiveKit Pod per node;
- correct externally reachable ICE address, firewall and NAT behavior;
- node placement and anti-affinity to prevent host-port conflicts;
- graceful drain and termination period during upgrades;
- separate TURN/TLS certificate and transport validation when needed.

Do not assume private/multi-layer-NAT nodes become viable WebRTC endpoints
merely by exposing an HTTP LoadBalancer. Test the actual client network.

## Acceptance stages

1. Complete public Compose acceptance: trusted certificates, enrollment,
   telemetry, restart/restore and actual media connectivity.
2. Build single-Gateway k3s delivery: complete frontend, managed backend,
   databases, initialization Job, Secrets, ingress and certificate resources.
3. Verify the same enrollment/authorization contract, denied requests,
   confirmation-loss recovery and vehicle retirement.
4. Verify certificate renewal, volume restore, Pod restart and media drain.
5. Only then assess HA: replace/rework Gateway's single-owner storage and check
   provider/database/Redis/session behavior before raising replicas.

One k3s node is not HA. Multiple application Pods do not establish database,
media or physical handover availability.
